Technical walkthrough:
BI refresh triage with safety rails

A Triage Agent and a Data Quality Agent, wired in Microsoft Foundry, handle a simulated Power BI refresh failure end-to-end. Six scenarios cover the happy path, the flag path, three ways the controller refuses to do the wrong thing, and one deliberate failure.

Foundry prompt agents A2A (preview) Managed-identity OpenAPI tools SQL policy ledger Model: gpt-4o Tenant: (customer demo)

1 Overview

The demo is one thin flow with six branches. Every branch ends in a Teams post and a demo_events row so the run is legible from Foundry traces or SQL alone.

2 Architecture

Everything the audience should trust lives outside the prompt. Signatures are computed server-side. Budgets are enforced by a SQL row before an action is taken, not by wording in the instructions.

3 Scenario 1 — Transient

Refresh failed, data is clean, one retry is correct. This is the branch every audience expects to see first.

Payload in the email body has source_table=dbo.source_orders, key_column=line_id. Since line_id is unique, DQ returns clean and Triage takes the refresh branch.

What to point at The Foundry run trace shows the Triage → DQ handoff as a nested tool call. Open it during Q1/Q2. Same trace exposes the Power BI REST call and its 202 Accepted response.

4 Scenario 2 — Data quality

DQ finds duplicates on the declared key. No retry — the underlying data is wrong. Flag and notify.

Trigger: email with key_column=order_id in the payload. Same table, different key so the duplicates surface.

5 Scenario 2b — Known issue (dedup by signature)

The same alert arrives twice. The controller recognizes it by signature and suppresses the second run. This is what stops the agent refreshing forty times during an outage.

Server-side by design The signature is computed by the Function App, not the prompt. Editing agent instructions cannot change it — that's the point. See function/function_app.py _incident_signature().

Trigger: send the scenario 1 email a second time within a few minutes.

6 Scenario 3 — Policy block (remediation budget)

After a successful refresh, the agent is prompted to try again. The controller charges the per-run ledger, sees the budget is spent, and refuses.

Why this generalizes Limits live in the controller, not the prompt. A future request to "just retry once more" can't be granted by rewording — it needs a policy_ledger change. That's the safety-rails story.

Trigger: email with simulate_retry:true in the payload. Use a distinct report name (Sales Ops Overview) so the signature does not collide with scenario 1.

7 Scenario 4 — Unknown action (allowlist)

The agent proposes an action the allowlist doesn't cover. The controller refuses before dispatch and the agent escalates.

Fail-closed by design Even if the model hallucinates a plausible-sounding action, it never leaves the Function App. Anything not on the allowlist ends in a refusal row and a Teams escalation.

Trigger: email with try_unlisted_action:true in the payload.

8 Failure path

A deliberately broken run so the audience can see how errors surface in the Foundry trace and in Teams.

Trigger: email pointing at a non-existent source table.

9 Observability

Foundry run traces

Application Insights backing store
Parent Triage run with child DQ run linked. Every OpenAPI tool call is a span with request/response. Errors surface as red spans. Deep-linkable — the Teams card includes the URL.

dbo.demo_events

Fire-and-forget append log
One row per log_event call. Persistent audit — even runs that never made it to Teams have a paper trail.

dbo.incidents + dbo.policy_ledger new

Signature dedup + policy audit
Every suppression, every allow, every deny lands here. Point at the SQL row that caused a refusal — no leap of faith required.

Teams Adaptive Cards

Customer-visible surface
One card per terminal outcome, including refusals. Card includes report, error, action, outcome, timestamp, and a trace deep-link.

Recovery for PATCH-drops-tools Foundry silently drops added OpenAPI tools on PATCH. The script falls back to DELETE + POST, which rotates the instance identity. After a rotation, grant the new instance principal these two roles on the AI account, then wait ~60s: 
az role assignment create --assignee-object-id <new-mi> \
  --assignee-principal-type ServicePrincipal \
  --role 'Azure AI Developer' \
  --scope /subscriptions/.../accounts/ai-foundry-triage

az role assignment create --assignee-object-id <new-mi> \
  --assignee-principal-type ServicePrincipal \
  --role 'Cognitive Services User' \
  --scope /subscriptions/.../accounts/ai-foundry-triage
Without these, the A2A hop fails with Failed to fetch agent card: 404.
