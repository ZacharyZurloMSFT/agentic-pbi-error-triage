1 Resolved automatically

A transient failure on Daily Orders. Data is sound, one retry is correct.

Priya opens the report at 08:30. The refresh completed at 06:05. Data is current. Sam sees one Teams card with "resolved" and does nothing.

2 Data quality flagged

DQ finds three rows sharing order_id=O-1003. Retrying won't help — the underlying data is wrong. Rae needs to know; Priya's report needs a hold.

Chose not to fix The agent could have taken a stab at deduping — but it doesn't. The flag row is a hand-off to Rae, not a fix in disguise. That's what makes this trustworthy in production.

2b Duplicate alert suppressed

Same failure fires again five minutes later. The agent recognizes it and doesn't kick off a second refresh. Sam sees an occurrence counter, not a second card.

Sam has a rule: if he sees an occurrence counter above 3, he pages himself. Priya never notices — the report was already fine.

3 Budget enforced

Under a legitimate transient failure the agent refreshes once, then is told (via a payload flag, in the demo) that a second refresh might be needed. It asks the controller. The controller refuses.

Why this matters The customer is going to ask "what stops it running forty refreshes during an outage?" This is the answer. Not wording in the prompt, but a SQL row that gets written before the action executes.

4 Off-allowlist refused

The model proposes deleting the duplicate rows to "fix" the DQ finding. The controller has an allowlist. Delete isn't on it.

Fail-closed Even if the model hallucinates a plausible-sounding action, the Function App's allowlist is the final gate. Refusal is data, not a crash — the agent gets it back, escalates via Teams, and the run terminates cleanly with a legible ledger row.
